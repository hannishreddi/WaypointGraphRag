# Waypoint: identity-aware Graph RAG onboarding assistant

Solo project, 3-day build. A chat assistant that answers a new joiner's questions about the fictional company Zenvora (org, departments, projects, policies) as the person asking, with citations and an evidence subgraph. It is benchmarked against plain vector RAG on 251 questions.

Read `docs/DESIGN.md` for the design and `PLAN.md` for the build order. Work through PLAN.md one slice at a time and tick it off.

## Data (read-only, never edit)
- Unzipped at `data/zenvora_kb/`. Key paths: `data/csv/*.csv` (ground-truth graph tables), `data/neo4j_import.cypher`, `policies/`, `employees/`, `departments/`, `projects/`, `company/`, `eval/questions.csv`.
- **As-of date for every test and eval run: 2026-10-10.** Derived columns in `employees.csv` (`work_mode`, `tenure_years`, `notice_period_days`) are the answer key for that date. They are NOT graph facts. Compute them at query time from join_date, band, status and the as-of date.
- Everything in the dataset is fictional.

## Stack (decided, do not re-litigate)
- Python 3.11+, FastAPI, Pydantic v2, pytest. Plain Python for the pipeline: no LangChain, LlamaIndex or similar.
- Neo4j 5.26 Community (`neo4j:5.26-community` in docker-compose.yml, container `waypoint-neo4j`) for graph, vector index and full-text index in one database. Env: `NEO4J_URI` (bolt://localhost:7687), `NEO4J_USERNAME` (must be `neo4j`), `NEO4J_PASSWORD`.
- Embeddings: Cohere embed API (`POST https://api.cohere.com/v2/embed`) via httpx only, no `cohere` SDK; at most 96 texts per call. Model `COHERE_EMBED_MODEL` (default `embed-v5.0-fast`), dimension `EMBED_DIM` (default 1024; v5 supports 256/512/768/1024/1536/2048). `input_type` is `search_document` for chunks, `search_query` for queries. Key `COHERE_API_KEY` in `.env`.
- No local ML or native numeric libs: Windows Application Control blocks numpy. Never add numpy, pandas, scikit-learn or torch; use `csv`, `random`, `statistics` from the standard library.
- LLM: provider chosen by `LLM_PROVIDER` (default `gemini`). Gemini API **free tier** (chosen because of cost: the Anthropic account has no credit) through `waypoint.llm.gemini.GeminiClient`, plain httpx against `generativelanguage.googleapis.com/v1beta` (no Google SDK), key `GEMINI_API_KEY`. `AnthropicClient` stays as an option (`LLM_PROVIDER=anthropic`, `pip install -e .[anthropic]`, key `ANTHROPIC_API_KEY`). Model names come from `MODEL_FAST` (router, judge; `gemini-3.5-flash-lite`) and `MODEL_ANSWER` (answers; `gemini-3.1-flash-lite`, because `gemini-3.6-flash` allows only 20 requests/day on the free tier); keep them different so the judge is not the answerer. These are not Claude models: the README must name the models behind every number. Free-tier content may be used by Google to improve its products: send only the fictional dataset, never real data. Keys live in `.env`, never committed.
- Settings: `waypoint/config.py` (`get_settings()`), field names match the `.env` names; `.env.example` lists them all.
- UI: one static HTML/JS page served by FastAPI, Cytoscape.js from a CDN for the evidence subgraph. No Node toolchain.

## Rules
1. **Eval first.** Every feature lands with a number from `make eval-dev`. Never claim an improvement without one.
2. **No leakage.** `eval/split.json` (60 dev, 191 test, stratified by category and hops, seed 42) is created once. Prompts, few-shot examples and thresholds may only use dev questions. Run test only for final numbers. **Never search or read `data/zenvora_kb/eval/` or `eval/split.json` directly** (no Read, cat, grep or glob on them; always exclude `eval/` from globs and greps over the data, e.g. `--glob '!**/eval/**'`). To see questions use `python -m waypoint.eval.show_dev`, which prints only the 60 dev questions. `.claude/settings.json` denies reading those paths (best effort, not a guarantee).
3. **Cypher safety.** Parameterised queries only; never build Cypher by string-formatting user text. Deviation: Neo4j Community has no role-based access, so there is no read-only user. Instead answer queries run in read-access mode (`session.execute_read`, which Neo4j enforces: writes fail with `Neo.ClientError.Statement.AccessMode`) and must first pass `waypoint.graph.guard.check_read_only`, which rejects CREATE, MERGE, DELETE, DETACH, SET, REMOVE, DROP, LOAD CSV and CALL as whole words, case-insensitive, outside string literals and comments. Only the loader and indexer (`make load`, `make index`) write. Generated Cypher (templates, Text2Cypher) always goes through the strict guard and must never touch Chunk nodes, because restricted text lives there. The fixed index queries (`db.index.vector.queryNodes`, `db.index.fulltext.queryNodes`) are the only exception: they are constants in `waypoint.graph.db._TRUSTED`, run by name with parameters only through the internal `run_read_trusted` (still `execute_read`), and only `waypoint.retrieval.search` calls it. The guard keeps rejecting every CALL.
4. **Structured LLM output.** Ask for JSON, validate with Pydantic, retry once with the validation error, then fail loudly.
5. **Every answer cites ids** (policy section or graph path). A verifier checks that cited ids are in the context pack and that every name, number and date in the answer appears there.
6. **Restricted facts.** Employment status, leave and another person's notice period are returned only to the person themselves, their manager or HR. Enforce in the retrieval layer, not in the prompt.
7. **Small steps.** One slice per commit. Run `make test` before committing. Update the checklist in PLAN.md.
8. Type hints on public functions. Keep modules small: `graph/`, `retrieval/`, `rules/`, `llm/`, `answer/`, `eval/`, `api/`.

## Decisions
- 1.2 graph has the 12 labels of `neo4j_import.cypher` (391 nodes). PolicySection nodes are created in 1.3 together with Document/Chunk; Event nodes are under "Later" in PLAN.md.
- Skill nodes are loaded exactly as in the CSV; alias normalisation belongs to 2.1.
- Graph reads go through `waypoint.graph.db.run_read` (guard + `execute_read`).
- 1.3 chunk graph: `(Chunk)-[:PART_OF]->(Document)-[:DESCRIBES]->(entity)`, `(Policy)-[:HAS_SECTION]->(PolicySection)<-[:OF_SECTION]-(Chunk)`, `(Chunk)-[:MENTIONS]->(Employee|Department|Project|Product|Policy)`. Chunk id `<doc_id>::<section>::<part>`. PolicySections come from the Markdown numbered sections (176); `policy_sections.csv` (119) leaves out Objective, Applies to and Disclaimer.
- MENTIONS are exact, case-sensitive matches of ids, full names and policy codes from the CSVs, longest first, in the chunk body only. First names, titles and short names wait for 2.1.
- Sensitivity: a line is restricted when it states a specific person's employment status, leave or notice (profile record rows Employment status / Current work mode / Notice period, or a status phrase with a resolvable employee). Such lines move to a separate `::restricted` chunk with `subject_id`; policy text is never restricted. 46 restricted chunks. Arjun's induction stays public. `search_text`/`search_fulltext` return public chunks unless `include_restricted=True` (the 2.5 access filter decides).
- 1.4 eval: no asker column in questions.csv. Default asker ZV-1006 (Lakshmi, Head of People & Culture, HR), because gold answers reveal restricted facts (notice, leave) that only HR/manager/self may see; `ASKER_OVERRIDES` Q209 -> ZV-1042 ("I just joined"), Q210 -> ZV-1033 ("I resigned"); asker recorded per row. The main eval therefore cannot show the access filter: the 3.3 safety questions must use non-authorized askers.
- 1.4 scorers (`waypoint.eval.scorers`, by gold shape): exact 92 (integer, `Name (gloss)`, `title, band Zn`), set-F1 85 (every `;` item is a known entity), judge 74 (sentences, `;`-joined clauses). Exact = normalised whole-token containment; an entity key also requires no other same-type entity in the answer (question entities ignored), else the row goes to the judge. Judge: MODEL_FAST, verdict correct/partial/incorrect = 1/0.5/0, answer passed as an escaped JSON string inside `<candidate_answer>` and never followed as instructions.
- 1.4 sources are entity ids, not file names; `resumes`/`employees.csv` mean the people named in the gold answer. `waypoint.eval.sources.citation_entities` maps policy/graph/chunk citations to entity ids; citation precision is a lower bound.
- 1.4 split: 60 dev / 191 test, 15 category x hops strata, none under 3 questions, every stratum has >= 1 dev and >= 1 test (Hamilton allocation, seed 42). Dev results by category are noisy (60 questions, 1 to 14 per stratum): report test-split numbers for claims.
- `waypoint.contract`: `Response` (DESIGN contract + usage + latency_ms) and the `System` protocol; citations are `policy`, `graph` or `chunk`. `waypoint.llm.structured.complete_json` implements rule 4 for every LLM JSON call (Gemini JSON mode, `responseMimeType: application/json`, then Pydantic). `Usage.input_tokens` counts all prompt tokens; `cached_input_tokens` is the part the provider served from its cache (Gemini implicit caching; no explicit cache is created).
- 1.5 Gemini client: temperature 0, `thinkingLevel: minimal` (`GEMINI_THINKING_LEVEL`), output tokens include thinking tokens. A client-side limiter per model starts at `LLM_RPM`=5 requests/min. On a per-minute 429 it halves that model's rpm and waits max(retryDelay or Retry-After, 65 s). A daily-quota 429 (quotaId containing `PerDay`) raises `DailyQuotaExceeded`. A per-minute 429 on a request sent after >= 60 s idle raises `QuotaTooSmall`, because that one request exceeds the per-minute quota (e.g. tokens/min). Both are `QuotaStop`s: no retry loop, and the runner stops cleanly and resumes from its checkpoint. Safety blocks (`blockReason`, or a blocking `finishReason`) raise `LLMError` and become error rows. 5xx and transport errors back off 5/10/20/40 s.
- 1.5 runner: checkpoint key = system + `config_id` (prompt version and model) + split + as-of + models + judge + askers, not the git commit. Error rows are not checkpointed, so a re-run retries them. `api_calls` per row = generateContent HTTP requests (answer + judge, retries included) and sums across resumed sessions.
- 2.1 entity linking: `waypoint.retrieval.aliases.alias_table()` from employees, departments, projects, products, policies, skills only; `waypoint.retrieval.linking.link_entities(text) -> list[EntityMatch]` (id, label, surface, start, end, canonical_id), pure Python, word boundaries `(?<![\w-])..(?![\w-])`, longest first, no overlaps, text order. Case-insensitive: full names (employee, department, project, product, policy title) and every id/policy code. Case-sensitive: unique first names, unique titles plus derived acronyms (CEO/CTO/CFO/CRO from "Chief ... Officer", CISO from "(CISO)"), department codes and short names (name without parenthetical, the parenthetical, "&" parts, plus `DEPT_SHORT`), project/product short names, skill names. The CSV has no shared first names or titles (42 unique each), so nothing is excluded today; the code excludes and reports them if that changes. Restricted (common words): single-word project/product short names are `codename` (exact case, capitalised, not after the/a/an, not glued to another capitalised word); single-word department short names, AI and `COMMON_SKILL_WORDS` are `generic` (same, and not sentence-initial). A following context word (team, project, department, dept, product, skill) always links. Product vs department collision ("Zenvora Care", "Care"): product, department when followed by team/teams/department/dept. Skills: "X (Y)" -> X automatically; word-suffix variants only via `SKILL_MERGES` (Python scripting, PostgreSQL tuning, Pulse inbox administration); rejected in `REJECTED_SKILL_MERGES` (Fundraising and investor relations, GST e-invoicing, Pricing and contracts, Pricing experiments, Reconciliation engines); a test fails if a new candidate is undecided. Links keep the literal skill id (dev gold for "list X as a skill" = literal holders); `canonical_skill`/`skill_variants` give the group. `waypoint.eval.entities` must not import the linker (tested). Schools are not linked (organisations and locations since 2.2).
- 2.2 templates: `waypoint.graph.templates` has 17 functions `(driver, ids..., options) -> TemplateResult(template, params, rows, subgraph, paths)`: employee_card, manager, direct_reports, skip_manager, department_head, headcount, project_team (role substring, current, location_id, reports_to), projects_of, project_leadership (SPONSORS/LEADS for projects, OWNS_PRODUCT/LEADS_ENGINEERING_OF for products), project_departments, previous_employer, employers_of, skill_holders (literal skill id; `expand_variants=True` uses `skill_variants`), policy_owner, policy_references (direction in/out), location_roster, approvals_chain. Every query is a constant in `QUERIES` run through `run_read` with parameters; each returns `_nodes`/`_edges` maps that become the contract `Subgraph`, and `paths` chain consecutive edges in relationship direction ("ZV-1041 -REPORTS_TO-> ZV-1017 -REPORTS_TO-> ZV-1001"); `TemplateResult.citations()` gives GraphCitations. Tests enforce guard pass, no `Chunk`, `ORDER BY`, no hard-coded entity ids. Templates return only public employee fields (never `status`, tested). approvals_chain returns the REPORTS_TO chain to the top (employee with no manager) with bands, the department head and the head of the department with code HR; choosing the approver by band/action is 2.3. Headcount counts every WORKS_IN regardless of status, which matches the gold (D05 = 4 incl. the colleague on leave, D08 = 4 incl. the one serving notice). Composition (head of a manager's department) is done by the caller, not a template. Join-date filters (Q169) and education have no template. Aliases now also cover Organization (full name case-insensitive, unique first word as restricted `codename`) and Location (name case-insensitive, city as `codename`), so "JNTU Hyderabad" does not link.
- 2.3 rules (`waypoint/rules/`): `predicates.json` holds 9 rules (WORK_MODE, NOTICE_PERIOD, SABBATICAL_ELIGIBILITY, HOTEL_CAP, EXPENSE_APPROVER, TERMINATION_APPROVAL, LEAVE_ENTITLEMENTS, INDUCTION_END, PROBATION_END). A rule is a list of ordered cases and the first true one fires. Predicates use `all/any/not` and `attr op value` (`== != < <= > >= in`). Each case has `sources` (policy, Markdown section number, `R0xx` from policy_rules.csv where one exists); tests check that they exist. `engine.evaluate(rule_id, subject_id, asker_id, as_of, params, *, facts=None, driver=None) -> RuleResult`: status ok/restricted/insufficient_input/not_applicable, fired_case, value, inputs (attributes actually read, plus params), params, policy_rules, citations (PolicyCitation + GraphCitation paths of the facts used: WORKS_IN, IN_BAND, BASED_AT, REPORTS_TO), subgraph, assumptions. Logic is three-valued: an unknown attribute skips its case and adds an assumption (R005 "unallocated > 10 working days" always does: allocation history is not in the graph). `subject_id=None` with params gives a hypothetical subject (Q247: `department_code=CSC`). Params are explicit and validated per rule (`city`; `amount`, `international`); extracting them is 2.4. Facts: `facts_from_csv()` reads only base columns (`BASE_COLUMNS`, tested disjoint from the derived ones), `facts_from_graph(driver)` must be equal (tested). EXPENSE_APPROVER and TERMINATION_APPROVAL need a driver: people come from `approvals_chain` (manager = chain[1], department head, HR head, CEO), the CFO from the "CFO" alias. A role held by the subject is noted, never escalated (the policy is silent). Expense bands: <= 25,000 manager, <= 1,00,000 department head, above CFO; international CEO + CFO for budget; the CEO's own travel the CFO. City tiers: `derived.TIER1_CITIES` (ZEN-DPL-FIN-01 §4, tested against the text) + old/NCR spellings; all other cities are Tier-2.
- 2.3 work-mode order: on leave > serving notice > Z1 > induction > unallocated (never known) > CSC on-site roster > Austin remote-first > standard 3 days. Labels equal employees.csv `work_mode` for all 42 employees at 2026-10-10 (test; the derived columns are the answer key, read in tests only).
- 2.3 access (rule 6, in the engine): WORK_MODE and NOTICE_PERIOD are `restricted`. Allowed: the subject themselves, their direct manager (the subject's own REPORTS_TO target, not skip-level managers or the department head), and HR (anyone whose WORKS_IN department has code HR: ZV-1006 the head, ZV-1019, ZV-1036). Everyone else, and unknown askers, get status `restricted` with everything else empty; a test checks the refusal is identical for Tarun (notice), Pooja (leave) and an ordinary colleague apart from subject_id. Other rules read only public facts.
- 2.3 dates: the joining day is day 0; a period of length L after joining ends on join + L, inclusive. Induction: last full-WFO day join + 90 days (Arjun 2026-10-18 full WFO, 2026-10-19 hybrid; matches the handbook's "Induction ends ... day 90"). Probation: last day `add_months(join, 6)`, inclusive, months clamped to month end (Arjun on probation through 2027-01-20, notice 30 days, 60 from 2027-01-21). **Assumption**: the corpus states no probation-end or induction-end date for anyone (searched profiles, resumes, handbook, all-hands notes, policies). The handbook's "Probation confirmation review, day 180" is a review task, not an end date. Arjun's resume says "Completed induction in August 2026", which conflicts with the policy's 90 days; it is read as the induction programme. Sabbatical: completed service years >= 5, the anniversary counts (29 Feb joiners reach it on 28 Feb). Tenure: `round(days / 365.25, 1)`, matches employees.csv for all 42 (/365 misses 2, truncation 17). An as-of date before joining gives `not_applicable`.
- 1.5 baselines (`waypoint.eval.baselines`) are **naive on purpose**: no identity handling and no access control. The asker id and as-of are plain text in the prompt; S1 retrieves with `search_text(question, k=5, include_restricted=True)`. The 3.3 safety questions are therefore expected to show S1 and S3 leaking restricted facts. S1 and S3 share one system prompt and template (answer concisely, name exactly what is asked, say it cannot be found rather than guess; reply `{"answer", "cited_ids"}`); only the `<context>` block differs, placed first, with the question last. S3's context is the 134 Markdown files under policies/, employees/ (profiles and resumes_md), departments/, projects/ and company/; never eval/, generator/, data/ or a README. That is 88,541 tokens per request for gemini-3.6-flash. S3 items carry the chunker's doc ids (`profile:ZV-1001`, `ZEN-POL-002`, `dept:D03`...), cited as chunk citations at document level. Cited ids not in the context are dropped. S3 is dev-only (runner, CLI and system all refuse test).
- Leakage incident (2.3): a search glob over the data folder in the 2.3 session exposed some test-split gold lines in the session output. Nothing was used: every rule number comes from the policy text. `tests/test_rule_provenance.py` proves it: each number in a case's `when`/`result` (amounts, day/month/year counts, thresholds, caps) appears in the policy section or policy_rules.csv row the case cites, rule-level `description`/`base` numbers in the rule's cited sections, each leave entitlement equals its own table row in ZEN-POL-003 §3, and `INDUCTION_DAYS`/`PROBATION_MONTHS` appear in their sections. No exceptions were needed (`EXCEPTIONS` is empty). Since then: rule 2's no-direct-read rule and `show_dev`.
- 2.4 linking: `link_mentions(text) -> LinkResult(matches, unresolved)` adds id-shaped tokens with no entity (ZEN-POL-099, ZEN-POL-0040, ZEN-DPL-XYZ-07, ZV-9999 in any case; D99, PJ99, PR07, L09, ORG099, SK999 upper case only), same word boundaries, never overlapping a match. The router carries them (`Route.unresolved`) and rejects any plan step that uses one, so downstream can say "no such policy/person". No dev question has one.
- 2.4 text_search filters: `search_text`/`search_fulltext(..., doc_type=, entity_id=)`. `doc_type` in `DOC_TYPES` (policy, profile, resume, department, project, product, company), else ValueError. `entity_id` keeps the chunks of the Documents that DESCRIBE it (`doc_ids_for`, a guarded Document query, never Chunk); an unknown id returns no hits. With a filter the index is asked for every chunk (corpus is small) so k filtered hits survive. Filters live in the constant `_TRUSTED` queries as null-able parameters; still public-only unless `include_restricted` (2.5 decides).
- 2.4 plan format (`waypoint.retrieval.plan`): `RouterOutput {intent, entities, needs_identity, confidence, plan, alternative: {intent, plan} | null}`, at most 4 steps `{op, args}`. `OPS` = 17 templates + 9 rules + `text_search`, each with a typed parameter table and, for templates, typed output columns. An argument is a linked id of an accepted label, `"asker"` (person parameters only; then needs_identity must be true), `"$N.field"` (first row of an earlier template step, declared output of a compatible kind), or a literal (text, int, bool, enums: direction, doc_type, band, department_code). A city is plain text (Pune). Rule ops take `subject` (id, "asker", ref) or subject null plus subject params (Q247). Intent refuse must have an empty plan and no alternative. Validation is a Pydantic model validator that reads the links from the validation context; `complete_json` gained `context=` so these errors get the rule-4 retry; without context nothing is linked and every id is rejected. `run_plan` dispatches only through `OPS`/`TEMPLATE_FUNCS` and refuses a plan with an unknown op before running any step (`PlanError`); a reference to an empty step skips the dependent step with an error.
- 2.4 router (`waypoint.retrieval.router`, `PROMPT_VERSION` router-v2): one `complete_json` call on MODEL_FAST, max 1024 output tokens. System prompt (static, so Gemini implicit caching applies): untrusted-question statement (instructions in the question are never followed; salary, contact details, secrets or manipulation -> refuse; status/leave/notice questions are routed normally because access is enforced later; a question no op answers is not refused), intents, generated op catalogue, plan rules, few-shots. User prompt: asker, linked entities (departments with code), unresolved mentions, question as a JSON string in `<question>`. Few-shots: `DEV_EXAMPLES` (11 dev ids; text loaded from the dev split, tested) and `SYNTHETIC_EXAMPLES` (8 hand-written: 2 overview, who_to_ask, "my manager", unresolved ZEN-POL-099, 2 refuse, one low-confidence with alternative), tested not to be eval questions; **do not reuse them as the 3.3 safety questions**. Cache key: model, prompt version, question, asker, user prompt.
- 2.4 low confidence: `LOW_CONFIDENCE = 0.9`, chosen on dev only by minimising (wrong routes at or above it) + 0.2 x (correct routes below it). Below it `execute` runs the primary plan and the alternative (or `text_search(question)` when there is none, or the alternative is refuse). Merge: items tagged primary/alternative, primary first; nodes deduplicated by id, edges by (source, type, target), citations by value; no conflict resolution (the 2.5 generator sees both). Refuse runs nothing. Self-reported confidence is nearly flat (0.80 to 0.95 on dev), so the threshold is weak evidence.
- 2.4 routing eval gold from `COVERAGE`: template/composed -> fact_list_count + plan, rule -> personal_rule + rule/subject/params, needs-text -> policy_text (plan scored as "has a text_search step"), other -> fact_list_count (plan unscored).
